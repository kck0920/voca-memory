# 동기화 구현을 미루되, Revision 열은 지금 넣는다

크로스기기 동기화 자체는 후속 Phase로 미루지만, 동기화 대상이 될 **모든 테이블에 Revision(`rev`) 단조 증가 열과 `deleted_at` soft delete 열을 지금부터 넣는다.** 충돌 전략은 서버 중재 last-write-wins로 시작한다.

## 이유

`rev`와 `deleted_at`은 나중에 추가하기 매우 비싸다. 전 테이블 마이그레이션 + 이미 갔던 데이터를 채워 넣는 백필이 필요하고, 그 사이에 만들어진 데이터는 "rev 없이 들어온 행"이라 클라이언트 로직에서 예외 처리를 해야 한다.

이 비용은 지금 지불하는 편이 훨씬 작다. 두 열의 추가 비용은 사실상 0이다.

## 왜 LWW로 충분한가

Card 본문 편집과 복습 스케줄 갱신은 **같은 사용자가 대개 한 기기에서** 일어난다. 동시 편집 충돌은 드물고, 충돌이 나도 어느 쪽이 맞는지는 대개 자명하다. 진짜 어려운 것은 전체가 아니라 향후 다중 기기 실시간 협업이다 — 그때는 `rev`가 CRDT(`yrs`)로 교체될 접합부가 된다. 지금 그 복잡함을 미리 끌고 오지 않는다.

## 반드시 동기화 대상이어야 하는 것

Card 본문만 동기화하면 안 된다. **Memory State도 동기화 대상**이다 — 폰을 바꾸고 Due 목록을 받으면 복습 일정이 통째로 뒤집힌다. `card_states`는 `rev`를 가져야 하며, `review_log`는 Streak과 통계를 재현할 수 있게 한다.

## 대안의 함정

"일단 sync 없이 만들자. 필요해지면 그때 sync 엔진을 붙이지." 이러면 처음부터 로컬 전용 SQLite에 데이터를 쓰게 되고, 그때 오프라인 쓰기 충돌을 처리하는 코드를 처음부터 다시 짜야 한다. 지금 열 두 개를 넣는 것보다 비싸다.
