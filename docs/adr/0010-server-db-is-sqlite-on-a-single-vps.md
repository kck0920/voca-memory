# 서버 DB는 단일 VPS의 SQLite 파일이다

배포 서버는 **한 대**이고, 그 위에 SQLite 파일 하나를 둔다. WAL 모드로 돌린다. 관리형 DB를 쓰지 않는다.

## 왜 "SQLite는 다중 인스턴스에 위험하다"가 이 프로젝트에는 해당하지 않는가

그 문장은 사실이지만, 이 프로젝트의 전제와 맞지 않는다.

- 직접 운영하지 않는 개인 프로젝트다. 요청을 나눠 부하를 분산할 다중 인스턴스 구조가 나올 일이 없다.
- SQLite는 수천 개의 동시 리더 + **단일 라이터**를 문제없이 처리한다. 어휘 앱의 쓰기 부하는 사용자가 Rating을 누를 때 한 건씩이다. 병목이 되는 종류가 아니다.
- 로컬(Tauri)에도 SQLite가 필요하다. 서버도 SQLite면 **같은 dialect, 같은 SQL, 같은 저장소 trait**을 쓴다. Postgres를 택하면 이 프로젝트의 핵심 가치인 오프라인과 정면으로 충돌한다 — 로컬에 SQLite가 있어야 하니 SQL을 두 번 써야 하고, 마이그레이션을 두 벌로 돌려야 한다.
- `sqlx`의 컴파일 타임 쿼리 검증을 유지한다. `turso` 크레이트를 쓰면 `sqlx`를 버려야 한다.

## 배대가 생기는 대가

- **파일 백업이 곧 데이터 백업이다.** `rsync` + cron으로 설정한다. 복구 지점은 하나뿐이라 셋업이 단순하다.
- **배포 시 스키마 마이그레이션을 한 곳에서만 돌리면 된다.** 잠금 파일이 두 개로 늘어나지 않는다.
- 쓰기 직렬화 때문에 트래픽 급증에 취약하다. 하지만 그 전에 다른 것들이 먼저 무너진다.

## 되돌리는 조건

- 동시 쓰기가 필요해지면 (지하철에서 오프라인으로 공부하다 동시에 서버에 쓰는 사람이 늘면) Turso로 간다. 그때 `voca-store` trait이 있으므로 교체 지점은 한 곳이다.
- **P000 = 쓰기가 둘 이상 경로에서 오는 순간.** 로컬 캐시가 생기면 SQLite 파일은 단일 진실 공급자가 아니다.
